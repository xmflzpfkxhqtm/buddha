## TL;DR

1. `data/` 폴더(경전 .md/.txt 4,796개)를 **Supabase Postgres `scriptures` 테이블로 이전**
2. `/api/scripture`, `/api/scripture/list`, `/api/global-search` **API가 DB 기반으로 바뀜**
3. Vercel 번들에서 `data/` 제외 → 250MB 초과 문제 해결
4. `documents` 테이블(벡터) 복구 — `embedding_half` backfill (102,513 row) + **중복 청크 19,301개 제거** + HNSW 인덱스 재생성 (727 MB)
5. 앞으로는 `/api/embed`로 문서 넣으면 **트리거가 자동으로** `embedding_half` 채움

## 무슨 문제가 있었나

### 1. Vercel 배포 실패
- 오후 hong 브랜치 머지 후 Vercel 빌드가 `Serverless Function unzipped > 250 MB`로 실패
- 원인: `data/` 폴더가 211MB + `.md` 대량 추가되면서 Next.js 파일 트레이싱이 이걸 다 번들에 포함

### 2. 프로덕션 쿼리 10초 타임아웃
- Vercel **Fluid Compute가 설정만 되어 있고 실제 배포에 적용 안 된 상태** (Fluid Compute는 새 빌드부터 활성화되는데 hong 머지 후 빌드 실패해서 계속 예전 방식으로 돌고 있었음)

### 3. Supabase `documents` 테이블 상태 망가짐
- `embedding_half` 컬럼이 **전체 NULL** (halfvec HNSW 인덱스를 무용지물로 만드는 상태)
- HNSW 인덱스는 929MB로 존재했지만 실제로는 비어있음
- **Autovacuum이 4시간째 돌면서 DB I/O 점유** → 모든 쿼리 느려짐
- dead tuple 153,693개 (live tuple과 거의 같은 수) 누적
- VACUUM / ANALYZE **한 번도 실행된 적 없음** → 쿼리 플래너 통계 전무

## 뭘 고쳤나

### 1. `documents` 테이블 복구

| 단계 | 내용 |
|---|---|
| ① | autovacuum 취소 + 테이블 레벨에서 일시 비활성 (`autovacuum_enabled=false`) |
| ② | 무용지물 HNSW 인덱스 drop (929MB) |
| ③ | `embedding_half` 대량 backfill (102,513 row × `embedding::halfvec`) |
| ④ | `VACUUM ANALYZE` 실행 — dead tuple 153,693 → 0, 통계 업데이트 |
| ⑤ | HNSW 인덱스 재생성 완료 (`m=16, ef_construction=64`, **727 MB**, 빌드 49분 50초 소요) |
| ⑥ | **자동 채움 트리거 추가** — 앞으로는 코드가 embedding만 넣어도 DB가 알아서 halfvec 계산 |
| ⑦ | `match_documents` 함수 교체 — halfvec 인덱스 활용하도록 |
| ⑧ | autovacuum 재활성 |
| ⑨ | **중복 청크 정리**: hash 기준 MIN(id)만 남기고 DELETE — **102,513 → 83,212 rows** (19,301 중복 제거) |
| ⑩ | `VACUUM ANALYZE` 진행 중 (HNSW 인덱스 vacuum 단계에서 장시간 소요. **pgvector HNSW의 알려진 느림 이슈**. 서비스 영향 없음, 백그라운드 대기) |

### 2. 경전 파일 → DB 이전

- 새 테이블 생성
```sql
create table public.scriptures (
  id bigserial primary key,
  title text unique,      -- 파일명 확장자 제외, NFC 정규화
  filename text,
  format text,            -- 'md' | 'txt'
  subfolder text,         -- 'scripture' | null
  content text,
  created_at timestamptz default now()
);
create index scriptures_title_idx on public.scriptures (title);
create index scriptures_content_trgm_idx on public.scriptures 
  using gin (content gin_trgm_ops);  -- ILIKE '%q%' 빠른 검색
```
- `data/` + `data/scripture/` 전체 스캔 후 upsert: **4,796 rows / 191 MB**
- `.md`와 `.txt`가 같은 제목으로 있으면 `.md` 우선
- NFC 정규화까지 일괄 처리 완료

## 남아있는 이슈 / 추후 작업

### ✅ (완료) `documents` 테이블 중복 청크 정리

**결과**: 102,513 → **83,212 rows** (19,301 중복 제거, 약 **18.8% 감소**)

**원인 분석**: 재임베딩 시 기존 행을 삭제 안 하고 재삽입해서가 아니라, **한 번의 embed 실행 안에서 동일한 chunk가 수십~100개씩 insert**됨 (chunking 단계의 dedup 미작동). 일부 hash는 최대 106개까지 중복.

**실행한 정리**:
```sql
delete from public.documents d
where d.id not in (
  select min(id)
  from public.documents
  group by metadata->>'hash'
);
```

**남은 작업**: VACUUM ANALYZE 진행 중 (현재 실행됨, HNSW 인덱스 vacuum 단계에서 장시간 소요). 백그라운드라 서비스 영향 없음.

> ⚠️ **재발 방지**: 재임베딩 로직에서 **같은 배치 내 동일 hash chunk 중복 제거**가 필요. `saveDocumentBatch` 호출 전 `hash`로 dedup 또는 DB UNIQUE 제약 추가 고려.

### 🟡 Medium: 임베딩 중복 호출

`/api/ask` → 응답 받음 → `/answer` 페이지 이동 → `/api/search` 한번 더 호출. 같은 질문에 **OpenAI 임베딩 2번** 생성 (비용 + 로딩 시간).

개선 방안: `/api/ask` 응답에 hints 포함 → `/api/search` 호출 제거.

### 🟡 Medium: `/api/embed` 데이터 소스

현재 코드가 `fs.readFile('data/scripture/...')`로 파일에서 원문 읽는데, 프로덕션 번들에는 `data/`가 없음. 즉 **프로덕션에서 `/api/embed` 호출 시 파일 없음 에러** 발생. 로컬에서만 사용한다는 전제로 당분간 유지.

## 기술 메모 (나중에 같은 작업 할 때 참고)

### HNSW 인덱스 재생성 시 팁

1. **Direct connection(IPv6 only) 안 됨** — Mac에서 호스트 resolve 실패
2. **Session pooler URL 사용** (DATABASE_URL에서 포트 6543 → 5432)
3. **Supabase SQL Editor는 60초 HTTP 타임아웃** — 긴 쿼리에 부적합
4. **Pooler도 statement_timeout=120초 기본값** — 명시적으로 0으로 해제 필요
5. **`maintenance_work_mem` 기본 64MB** — HNSW 빌드에 너무 작음. SET으로 256MB 정도 권장 (512MB는 shared memory OOM)

올바른 명령 예시:
```bash
export SESSION_URL=$(grep ^DATABASE_URL .env | sed 's/:6543/:5432/' | cut -d= -f2- | tr -d '"')
psql "$SESSION_URL" <<'SQL'
set statement_timeout = 0;
set maintenance_work_mem = '256MB';
create index concurrently documents_embedding_half_hnsw_idx 
  on public.documents using hnsw (embedding_half halfvec_cosine_ops) 
  with (m = 16, ef_construction = 64);
SQL
```

### Supabase 디스크 현황 (2026-04-24 기준)

- Plan: Pro, 8 GB gp3 storage (autoscaling)
- Used: 5.41 GB (DB 3.3 GB + WAL 1.97 GB + System 0.14 GB)
- scriptures 테이블 추가분: +~200 MB → 약 5.6 GB 예상
- documents 테이블 중복 정리하면 **1.5 GB 정도 회수 가능**
